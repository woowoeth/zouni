## 零·五、产品取舍原则（判断做不做的依据）

这些原则来自一次完整的产品审视（见 `zouni-product-judgment.md`），是决定"加不加这个功能"的标准。

### 核心价值：省掉用户做攻略最耗时的三件事

用户找景点不难，小红书两小时就能刷一堆。真正耗时的是：

| 我们替他省掉的 | 判断标准 |
|---|---|
| **把景点排成一天走得完的顺序** | 时窗、车程、开放时间必须算过——这是信任的全部基础 |
| **算清楚钱够不够** | 逐项累加、两档预算、**含大交通提示** |
| **路上有变能自己改** | 遇雨、限流、时间不够能当场重排——这是差异化最强的一点 |

再加一条内容质量的分水岭：**"过期不候"信息不能漏**。布达拉宫提前 10 天预约、元阳只有 11–4 月有水镜、故宫官网 20:00 放票——漏一条用户就白跑一趟。

### 该做的：把"知道"变成"能做到"

产品最大的价值损耗在**执行断点**——信息给了，但用户还得自己去别处完成：

| 断点 | 现状 | 该怎么补 |
|---|---|---|
| 待办事项 | 223 条信息，**零个能直达** | 加官方链接，成本极低价值极高 |
| 住宿 | 给了区域和价格，**订不了** | 至少给地图深链 |
| 备选点 | 47 条里只有 10 条能真加入 | 补插入数据，或干脆别列 |
| 找线路 | 只能按目的地找 | **按月份找**——"我十月有假去哪儿"是高频问题 |

### 不该做的：三条明确的否定

| 不做 | 为什么 |
|---|---|
| **更多筛选维度** | 已有目的地/天数/预算/口味四个。再加"人数""难度"只会让选择变难——**选择成本本身就是成本** |
| **社区、点评、UGC** | 那是另一个产品。我们的价值是"给一份可信的、排好的方案"，不是再造一个小红书 |
| **精确到分钟的时间控制** | 旅行本来就不精确，**过度精确制造焦虑** |

### 广度与深度并行

内容广度（线路数）与执行深度（每条能不能真走）**同时推进，互不等待**：

- **深度**优先做执行断点——待办直达、按月份筛选、备选点补全
- **广度**按《省份深度规划》推进，一次多条而非一条条来
- 判断新功能时问一句：**这是在补断点，还是在加维度？** 补断点做，加维度不做

### 节奏：工具驱动，不靠记性

```bash
node zouni-tools/proposal-scan.js     # 自动扫出候选 → 生成 zouni-proposals.md
```

**为什么改成这样**：原来写的是「每周一次我准备提案单」，实际**一次都没做过**——因为它依赖我记得。现在扫描自动化，我只补判断，你只需逐条回「做 / 缓 / 否」。

触发时机：你说「接下来做什么」时、或每完成一批内容后。

### 提案来源（脚本扫，不靠印象）

| 来源 | 扫什么 |
|---|---|
| **覆盖度缺口** | 单方案族数量、无插入能力的线路数——来自体检报告的 ℹ 项 |
| **沉没能力** | 引擎已实现但 UI 层引用 ≤2 处的功能（做了没用上，接个入口就有） |
| **内容缺口** | 省份覆盖率、海外线路数 |
| **旅程断点** | 走查「挑→排→改→存→分享→出行」，找需要离开产品才能完成的事 |

### 提案单格式（每条必须写全，缺项不递）
```
【问题】现在用户遇到什么 / 差什么
【证据】截图、体检报告某项、或具体场景复现路径
【方案】做什么，做到什么程度
【工作量】小(半天内) / 中(1-2 天) / 大(需拆期)
【风险】可能影响什么、要动哪些红线
【不做的理由】如果我建议不做，理由写这里
```

### 你的审核动作
每条只需回三个字之一：**做 / 缓 / 否**，加一句优先级或补充。通过的进 backlog，我排期。

### 生产方式：工厂闭环（`zouni-tools/route-factory.js`）

内容生产不靠手写核对，走 **生成 → 验收 → 只有全过才进库** 的闭环：

```bash
node route-factory.js verify all              # 全量体检（已并入十连测第 10 项）
node route-factory.js derive --src xz7 --keep 0,1,2,6 --id xz4   # 派生变体，自动算派生量
node route-factory.js batch specs.json        # 批量候选，自动筛掉不合格的
```

**机器负责**（15 项自动验收）：住宿链项数与 nights 一致、末天为 null、天签连号、地图 seg/tonight 长度与索引、节点坐标、两档预算不超支（精打档自动触发省钱逻辑）、逐日不超时窗、无 NaN、预算档递减、**地理连续性**（前一天住哪 = 后一天从哪出发）、无假承诺。派生时还自动计算 lodges / nights / seg / tonight / rent / roadfood 并试算建议预算。

**我负责**：选哪几天、写文案（why / vibe / must / 一句话卖点）、判断内容是否讲得通。

**闭环的实战证明**：首次批量 6 个候选全部通过结构验收，但人工一看 3 条讲不通（从莫尔道嘎跳到黑山头、人还在雨崩就到了香格里拉、已在丽江却"回丽江"）。把这个判断形式化为「地理连续性」加进验证器后，机器**精确筛掉了同样的 3 条**——人工发现的规律沉淀成了机器规则。同一条规则还挖出一个一直存在的老缺陷：稻城 6 天版的 D1/D2 名字重复、地图缺康定节点。

### 数据结构：三层库 + 编译器（`zouni-tools/route-compiler.js`）

**分工原则：内容我维护，编排机器推导。**

| 层 | 内容 | 谁维护 |
|---|---|---|
| **CITY** 74 个 | 城市/节点：名称、地图坐标、住宿选项 | 我（新地方才加） |
| **POI** 188 个 | 站点：时长、价格、类别、vibe、must、chips | 我（新地方才加） |
| **LEG** 230 条 | 城市间接驳：里程、时间、费用、途经 | 我（新路段才加） |
| **声明** | 每天：从哪→到哪、玩哪些站点、住哪 | 我（一行一天） |
| ↓ 编译器 | **天签连号 · 住宿链与末天 null · nights · map.seg · map.tonight · map.order · 接驳查表 · 里程合计 · 地理连续性** | 机器 |

```bash
node route-compiler.js extract           # 从现有线路反向建库（已提取，无需手抄）
node route-compiler.js compile plan.json # 声明 → 完整路线对象
node route-compiler.js roundtrip all     # 往返验证（已并入十一连测第 11 项）
```

**为什么要这么改**（数据支撑）：324 个站点实例只有 188 个唯一站点、110 条接驳被重复录入、共 1446 个手工维护字段。而全部事故都集中在编排层——地图 seg/tonight 300 项出过 4 次错、天签 150 项出过 2 次错。这些字段**本来就该是推导出来的，不该手写**。

**等价性已验证**：把现有 26 条反向转成声明再编译回去，天签/住宿链/nights/seg/tonight/站点序列**逐字段等价**。这意味着编译器有能力接管全部编排，新线路可以只写声明。

**地理断裂在新架构下不可能发生**：声明里"上一天住哪"与"下一天从哪出发"是同一个字段推导出来的，结构上无法错位（旧架构靠事后检查才能发现）。

### 完整工具链：意图 → 上线

```
意图（去哪几城 · 几天 · 什么偏好 · 预算）
   ↓ route-planner.js    选点排日程（时窗 + 预算 + 偏好约束）
声明（每天：从哪→到哪 · 玩哪些站点 · 住哪）
   ↓ route-compiler.js   推导编排层（天签/住宿链/nights/seg/tonight/order/接驳）
完整路线对象
   ↓ route-factory.js    15 项验收
进库 → 十一连测 → 发布
```

| 工具 | 职责 | 我出什么 |
|---|---|---|
| `route-planner.js` | 天数分配、选点、**餐饮按用餐窗口**、**住宿按偏好预算选**、时段排序、可行性预检 | 意图（一个 json） |
| `route-compiler.js` | 编排层全部推导；三层库提取与合并 | 无（全自动） |
| `route-factory.js` | 15 项验收 + 派生变体 + 批量筛选 | 无（全自动） |
| `infer-poi-meta.js` | 从文案推断偏好标签与最佳时段 | 抽查校正 |

**四个人工层，都是"只增不改、永不被覆盖"的资产**：

| 文件 | 放什么 | 为什么需要 |
|---|---|---|
| `lib-override.json` | 补城市住宿、补路网缺失的接驳段 | 现有行程没覆盖到的数据 |
| `poi-meta-override.json` | 校正标签与时段推断 | 规则推断有 ~15% 误判率 |
| 声明里的文案 | why / vibe / must / 一句话卖点 | 真实世界知识，机器编不出 |
| 库里的新站点 | 新地方的时长、价格、文案 | **我唯一必须做的事** |

**编排覆盖景 · 食 · 宿三层**：
- **景点**：必看优先占坑，其余按「优先级 × 偏好匹配 ÷ 时长」贪心，装到 18:30 舒适线
- **餐饮**：不当景点排，落在真实用餐窗口（午餐 11:30–14:00、晚餐 17:30–20:30），每窗口一家；爱吃的（偏好含美食）挑好的，否则挑性价比
- **住宿**：躺平型选好房、预算紧选便宜的、其余给二选一让用户定；不再永远取第一个

**系统会诚实报缺口，不会瞎编**（实测）：
- 规划桂林 5 天 → 拒绝产出：「库里内容只够 2 天，要排 5 天需补约 14.8 小时内容（约 8 个站点）」
- 编译时发现龙脊→阳朔无直连 → 报错而不是假造一段路
- 编译时发现桂林无住宿数据 → 报错而不是随便填一家

**这正好服务于补到 100 条的目标**：规划器变成了内容缺口探测器——告诉我哪个城市缺多少内容，我照着补即可。

### 每条新线路的生产标准（六项，缺一不可）
1. **Schema v2 三件套**：`transport` / `locale` / `stay`（旧字段由 `normRoute` 反写，不手写）
2. **逐日行程**：站点、时窗、接驳、住宿链（`lodges` 项数 = 天数，末天 `null`）
3. **地图**：`nodes` / `order` / `seg`（长度 = 天数）/ `tonight`（长度 = 天数）；往返段自动弧线分离
4. **价格两处同步**：路线 `budgets` + 首页卡片文案
5. **i18n**：中英双写；路线级建议挂 `i18n:{en:{...}}` 覆盖层
6. **至少 1 个可插入备选点**：插到哪天、接哪个站后、时长、价格、前后接驳、一句话推荐

写完跑第 2、8 项验证，更新内容矩阵。

## 四、工程线：八步审查（不可跳）

```
① 侦察 → ② 划界 → ③ 预检 → ④ 落盘 → ⑤ 回归 → ⑥ 眼验 → ⑦ 同步 → ⑧ 发布
```

**⑧ 是默认动作，不是可选项**：每轮改动做完、测试全绿，就直接更新到线上，不攒批次、不等你催。没发布 = 这轮没做完。

| 步 | 动作 | 审查产出物（证据） |
|---|---|---|
| **① 侦察** | 读出待改处的**真实文本**，不凭记忆 | 贴出实际代码片段 |
| **② 划界** | **确定最小改动范围**：列出要动的文件/函数/规则，以及"确认不动"的边界 | **在报告里写一句「这次动了什么、没动什么」**——曾经只在心里想，没有产出物，所以形同虚设 |
| **③ 预检** | 两阶段补丁：所有替换先 `count==1` 全量校验，**全过才写盘** | 预检通过/失败的明确输出 |
| **④ 落盘** | 改在原位；删 CSS 必须整条规则删 | 落盘确认 + 语法检查通过 |
| **⑤ 回归** | 按影响面跑对应回归项 + 九连测；**新功能必须同时新增断言** | 回归清单勾选 + 九连测输出 |
| **⑥ 眼验** | 改了界面必须 headless Chrome 真渲染截图，我先看；**改布局必跑第 16 项全量扫描** | 截图 + 扫描输出 |
| **⑦ 同步** | 五产物 + 站点包 + 文档同步，版本号递进 | 产物清单 |
| **⑧ 发布** | 九连测全绿 → 推送上线 → **线上真浏览器复验** → 报告"改了什么/根因/怎么验的/影响面多大/什么没做" | LIVE_URL 复验结果 + 说明 |

**"改好了"三个字，必须以截图为凭。** jsdom 没有布局引擎，测不出排版。

### 抽样不算验证

反复出现「我说改好了、你在真机上发现还是坏的」，根因是**我用抽样代替了全量**：改 CSS 只截一两个位置、首页 18 张卡从没逐张点过、34 条线路只抽查两三条。

第 16 项全量扫描就是为此建的，它跑的是**用户真会做的每一个动作**：

| 覆盖 | 做什么 |
|---|---|
| A | 首页**每一张**卡片逐张点击，必须都能出行程 |
| B | **每条线路的每一天**逐天切换，内容必须渲染且天签高亮 |
| C | 每天里**每一个**可点元素都点一次，验证不抛错 |
| D | 布局异常自动识别：按钮与文字错位 >6px、文字被裁、横向溢出 |

### 修个案要升级成规则

三亚统计区重复天数这个问题，成都那轮已经犯过一次——我当时只修了成都那一条，**没写一条规则去扫全部线路**，所以三亚又犯。这是最典型的流程漏洞：

> 每修一个 bug，都要问：**同类问题在别处存不存在？** 存在就写成自动检查，而不是逐个修。

第 17 项交叉一致性体检就是按这个原则建的——它不查「有没有违反已知规则」，而是查「**同类信息之间对不对得上**」：卡片标价 vs 精打档预算、卡片天数区间 vs 该族实际方案、meta/title 的天数 vs 实际天数、口味引用的站点 vs 真实站点、双语文案是否成对。单条看都合法，只有横向比对才暴露。

**一次跑出 4 类真问题**：xj10 卡片标价 ¥5900 而预算是 ¥6800、9 张卡片天数区间没跟上新增变体、2 处 defSels 引用了不存在的站点、3 个卡片文案 key 还是族名。

**建完立刻做了回归验证**：把已修的卡片指向 bug 故意注回去，扫描准确报出；同时多抓到一个我不知道的问题（稻城线接驳文字被截断）。**能抓到已知 bug 的测试才算数。**

### 最小改动范围三条纪律
1. **只动必须动的**：你说改 A，就只改 A。发现 B 也该改 → 先说，你定，另开一轮。
2. **改动要可局部化**：优先改单个函数/单条 CSS 规则，避免改公共层（token、统一层、委托链）；必须改公共层时，在报告里明确标注"这次动了公共层"。
3. **改完能说清没影响谁**：说不清影响面 = 改动范围没划清楚，回到 ②。

### 影响面 → 必跑回归项
| 你动了什么 | 必跑 | 为什么 |
|---|---|---|
| **单条线路数据** | 第 2 引擎仿真 + 第 8 数据体检 + 卡片价格对账 | 时刻/预算/住宿链/地图易错位 |
| **引擎逻辑**（resolve/totals/normRoute） | 第 2 全量仿真 + 第 4 冒烟 + 抽 3 条线人工核对费用 | 一处改动波及 21 条线 |
| **CSS**（任何） | 第 6 视觉回归 + 第 9 可访问性 + **三页截图肉眼过** | 孤儿规则、裁切、对比度、焦点环都在这里翻车过 |
| **公共层**（token / 统一层 / 组件基类） | 第 6 + 第 9 + 全 Tab 截图 + E2E | 影响面最大，必须全量视觉复验 |
| **交互委托**（click 链、handler） | 第 7 E2E 真点击 + 第 4 冒烟 | 新分支被前面分支截胡是已知坑 |
| **i18n 字典 / 文案** | 第 3 静态终检（双写对账）+ 中英切换冒烟 | 单边写入、键缺失、函数名遮蔽 |

| **发布装配**（PWA/SW/站点包） | 第 5 三文件冒烟 + 线上复验 | file:// 与 https 行为不同 |

## 四·五、规模化：数据涌入时怎么不崩

**已实测的容量边界**（第 12 项性能守卫每次自动复核）：

| 维度 | 实测 | 判定 |
|---|---|---|
| localStorage | 上限 5120KB，单份行程 0.6KB | 可存 **8500 份**，无风险 |
| 首页渲染 100 张卡 | 8.8ms · DOM 1148 节点 | 无风险 |
| 搜索（300 条规模） | 0.36ms | 无风险 |
| 引擎重排 | 1.3ms | 无风险 |
| 十二连测总耗时 | 29 秒（26 条） | 100 条约 110 秒，可接受 |
| **单条线路数据量** | **7.65KB** | **唯一瓶颈：决定单文件承载上限** |

**单文件承载上限 ≈ 65 条**（600KB 体积阈值 ÷ 7.65KB）。超过就要分层交付：

| 版本 | 内容 | 触发条件 |
|---|---|---|
| **单文件版**（微信直发） | 精选 40–60 条，控制在 500KB 内 | 一直保留，这是产品的便携性优势 |
| **站点版**（HTTPS） | 全量，数据按族分片 + 点击时按需加载 | **线路数 > 65 或体积 > 600KB 时启动** |

分片方案（备好不实施，避免过早优化）：首屏只载引擎 + 卡片元数据（约 100 条 × 200B），点开某条线路才动态加载对应族的详情数据。

**健壮性已验证**（第 12 项守卫）：
- **坏数据不拖垮全站**：5 种畸形数据（缺 days、住宿链错位、seg 越界、预算为 0）加载失败后，后续线路照常可用
- **错误边界**：`safeLoad()` 捕获异常 → 退回上一条可用线路 → 明确提示"这条线路暂时打不开"，不白屏、零未捕获异常
- **无竞态**：200 次快速切换语言/货币/Tab，零错误、状态完整
- **存储降级**：localStorage 被禁用或写满时功能继续可用

**为什么现在不做分片**：26 条 317KB，距离阈值还有一倍余量。按「最小代价」原则，方案备好、守卫盯着，到线才动手。

## 四·六、跨端准备（小程序 / H5 / Web 共用一套核心）

**现状已就绪**（第 13 项守卫每次复核）：

| 层 | 体积 | 浏览器依赖 | 小程序能否复用 |
|---|---|---|---|
| 数据层 + 引擎层 | 148KB | **零** | ✅ 直接搬，一行不改 |
| UI 层 | 56KB | document 28 · innerHTML 33 · classList 35 … | ✗ 按平台重写（web 用 DOM，小程序用 WXML） |

**实证**：33 条线路在纯 Node 沙箱（无 DOM、无 window、无 localStorage，等价小程序环境）完成装载、重排、算账，全部通过。

**将来做小程序时的分工**：
- **直接复用**：ROUTES 数据、normRoute 归一、resolveDay/resolveAll 排程、totals 算账、i18n 字典与 t()/fm() —— 这些是产品的核心资产
- **需要重写**：页面渲染（WXML/WXSS）、事件绑定
- **需要适配层**：存储（localStorage ↔ wx.setStorageSync）、分享（剪贴板 ↔ onShareAppMessage）、导航（URL scheme ↔ wx.openLocation）、剪贴板（execCommand ↔ wx.setClipboardData）

**现在就要守住的纪律**（否则将来搬不动）：
1. **引擎层禁止出现任何浏览器 API** —— 第 13 项自动拦截
2. **平台能力只能出现在 UI 层**，且集中在少数几个函数里，方便将来替换成适配层
3. **禁止高版本语法**（`?.` `??` `replaceAll` `flatMap` `at()`）—— 小程序基础库、微信 X5、老 iOS Safari 的共同底线

| 约束 | 为什么 |

## 四·八、与其他进程共存

线上仓库有另一个 SEO 工作流在往 `index.html` 注入 `<!--GEO:HEAD-->` 与 `<!--GEO:BODY-->` 两块（约 6KB）。我直接覆盖会把它冲掉、对方下次跑又加回来——来回打架，历史上还出过一次 merge conflict 被提交进 index.html。

**发布前必跑**：

```bash
node zouni-tools/preserve-external.js zouni-xj-10d.html <线上的 index.html>
```

它做三件事：从线上取回外部注入块、合进我的产物、检查有无冲突标记（有则中止发布）。

**封面的体积储备手段**（实测数据，到线才用）：地图缩略图只有实景的 19%（0.48KB vs 2.53KB），32 张全换能省 102KB。
但实景对首页第一印象的价值高于这 100KB，所以**顺序是：先只存卡片用的封面 → 再降尺寸质量 → 最后才考虑换地图**。当前 586KB，距阈值还有 64KB 余量。

**体积阈值为此放宽到 650KB**：600KB 是首开体感的线，多出的 50KB 留给外部注入，不占我的内容预算。真正该盯的是「单条线路数据量」那一项。

**每次接手前先拉线上代码比对**，确认自己的改动没被覆盖——这次查下来 v50 的七个特征全部还在，只多了 SEO 层。

## 四·九、让错误写不出来，而不是写完再抓

发布日志累计 34 次踩坑，按类归并后暴露一个事实：

| 次数 | 类型 | 版本 |
|---|---|---|
| **3 次** | 统计区首格与天数格重复 | v41 · v55 · v72 |
| **3 次** | 选择器/结构判断错（改了半天没生效） | v37 · v49 · v61 |
| **2 次** | 逻辑写反（remove 写成 add 之类） | v67 · v68 |
| 2 次 | 原生 API 兼容性 | v45 · v63 |
| 2 次 | 体积超阈值 | v53 · v57 |

**同一个错犯三次，说明守卫的方向错了。**

十九道测试全是「写完再抓」。抓得到，但每次都要返工，而且返工本身又会引入新问题（v72 那次修完统计区，又带出卡片天数区间不符）。

### 根治的做法：取消手写的机会

统计区首格原本是手写字段 `hero1v`，写「N 天」跟旁边的天数格重复太自然了。改成**引擎自动推导**：

```
自驾线 → 总里程（引擎本来就在算）
非自驾 → 地图节点数（片区数），只有一个节点时退回住宿晚数
```

改完之后 56 条零重复，**而且以后写不出这个错**——那个字段不再被读取。

图标同理：缺表的族原本全落到默认 `🗺`（曾有 21 个族长一个样），现在按线路的 cng 标签和交通方式自动推一个。

### 判断标准

每次修完一个反复出现的错误，问一句：

> **下次我还能写出这个错吗？**

- 能 → 只是加了检查，治标。想办法把手写改成推导、把多处改成一处
- 不能 → 才算根治

**能自动算出来的，就不要留手写字段。** 手写字段每多一个，就多一个我会写错的地方。

## 四·十一、功能数据密度（第 21 项）

雨天方案的教训：UI 做好了，全站却只有 4 处数据，56 条里 52 条点开是空的。**这类「有壳没料」测试全绿也查不出来，因为它不报错，只是没内容。**

所以加了第 21 项，把每个依赖数据的功能都算真实覆盖率：

| 判据 | 含义 |
|---|---|
| ≥80% | 健康 |
| 40–80% | 偏薄，要补料 |
| <40% | **空壳，要么补料要么撤掉 UI** |

首次扫描抓到 3 项，但逐个查完发现**两类要区别对待**：

1. **真空壳**：备选点写着「备着的还有 玩 22 · 吃 31 · 住 14」——这些数字是编的，库里根本没有，用户点不进任何一个。**这是假承诺，必须改**。现在如实说明：能加进当天的说能加，只能用「+1 天」排的说清楚。
2. **不是空壳，是判据错了**：二选一站点只有 10% 的天有——但没有 opts 的天根本不显示选择器，所以低覆盖是合理的（不是每天都必须有得选）。真正该查的是「**声明了有选择，点开却是空的**」。

**判据修正后：15 项功能全部健康，零空壳。**

### 这条规矩要记住

**做功能前先查数据密度**。有 UI 没数据比没这个功能更糟——用户点开一次就再也不信了。

**区分「没有」与「说有却没有」**。前者可以接受（不是每天都有二选一），后者是欺骗（说有 22 个备选却一个都点不进来）。

## 五、质量门禁

**自动九连测**（`bash zouni-tests/run-all.sh`）：语法 → 引擎仿真 → 静态终检 → 双冒烟 → 视觉回归 → E2E → 数据体检 → 可访问性。明细见发布清单第一节。

**人工真机**（只有你能做）：约 20 项，**必须在微信里点**。headless Chrome ≠ 微信 X5 ≠ iOS Safari。

### 缺陷分级（写进报告，不单独走流程）

原来定了 P0/P1/P2 标记，**从没用过**——因为它是额外动作。现在并进报告用语：报 bug 时直接说清严重程度和响应，不再单独标级。

| 严重程度 | 我的响应用语 |
|---|---|
| 报错、白屏、算错、点了没反应 | 「这个最要紧，先修」——停下手上的事 |
| 排版错乱、假按钮、文案骗人、可访问性不达标 | 「当轮修掉」 |
| 视觉细节、间距、文案 | 「攒一批一起改」 |
| 内容缺口 | 进内容矩阵，不占当轮 |

## 六、发布流程

**常态：每轮改动完成即发布**，不攒批次。唯一前提是**过审**。

```
九连测全绿 → 关键路径回归 → 眼验截图 → 发布 → 线上真浏览器复验
        ↑ 任一不过 = 不发布，先修
```

| 门槛 | 要求 | 谁来验 |
|---|---|---|
| 九连测 | 全绿，一项不过都不发 | 我（自动） |
| 关键路径 | 十条最小必过集（发布清单一·五节） | 我（自动）+ 你（真机） |
| 眼验 | 改了界面必须有截图，我先看过 | 我 |
| 线上复验 | 发布后真浏览器打开 LIVE_URL，验渲染与零报错 | 我 |
| 真机点检 | 微信安卓 / 微信 iOS / iOS Safari | **只有你能做** |

**我发布后线上就是可用的**；你的真机点检是加保险，不是发布前置条件（内测期）。公开推广前，真机点检必须补齐。

**发布频率有平台限制**：GitHub Pages 同一小时内推送十余次后会开始拒绝构建（表现为 `duration: 0` 的失败，与代码无关）。所以"每轮做完即发"要理解为**每轮攒齐再发一次**，而不是每改一处就推一次。详见发布清单「发布频率纪律」。

1. 发布：`GITHUB_PUBLISH_TOKEN='ghp_xxx' python3 /tmp/quickship_publish.py --dir zouni-site --name zouni`
2. 线上复验：微信打开 LIVE_URL 过人工清单，iOS 验"添加到主屏"
3. 回滚：重跑同名发布即覆盖；每轮产物都是完整快照

微信内 github.io 不稳时：`zouni-site/` 原样传国内静态托管或自有域名，代码零改动。

## 七、进化机制（这份 SOP 怎么变聪明）

> **总目标：用最小的代价和成本，提升效率与质量。**
> 每加一条流程/测试/规则前先问：它能防住什么真实事故？代价多大？
> 防不住具体事故的流程 = 仪式，删掉。跑一次超过 3 分钟的测试 = 没人跑，要么提速要么拆分。

### 1. 事故闭环（四步，缺一条就会复发）
```
现象 → 根因 → 修复 → 【红线 + 自动断言】
```
只修不写红线 = 下次还犯；只写红线不加断言 = 靠记性，迟早忘。
**已闭环的例子**：
| 事故 | 红线 | 自动断言 |
|---|---|---|
| 微信白屏 | 禁 `?.` 等新语法 | 静态终检第 ⑤ 项 |
| 排版全乱 | jsdom 测不了排版 | 视觉回归第 6 项 |
| 左列按钮没边框 | 裁切容器内用内描边 | 第 9 项 + 截图 |
| 文案承诺"可加"却加不了 | 承诺必须有数据 | 静态终检第 ⑧ 项 |
| 焦点环被覆盖 | 末尾高特异性兜底 | 第 9 项真实 Tab |

### 2. 复盘：焊进发布流程，不设周期

原来定了「每次发布 5 分钟 / 每周 15 分钟 / 每月 30 分钟」，**三条全部零执行**。原因很实在：我没有跨会话的时间感，"每周"对我不成立。

改成发布时强制记录：

```bash
node zouni-tools/release-log.js --ver v43 --what "改了什么" --bug "踩了什么坑" --guard "升级成哪条守卫"
node zouni-tools/release-log.js --check    # 发布前查上次复盘是否完整
```

只问三件事：**改了什么 · 踩了什么坑 · 坑是否已升级为自动守卫**。

日志会自己算账：「累计 N 次发布，M 次踩坑，K 次升级为守卫」。**M > K 就是在重复踩坑而没有沉淀**——这个数字比任何自我评价都诚实。

### 3. 外部学习
每月至少读一份外部优秀规范（设计系统、产品文档、工程实践），**逐条对照我们实测**，不是照抄。
已做两次：
- Vercel 设计规范 → 抓出对比度不达标、表格无语义、焦点环被覆盖
- jakubkrehel/skills（UI 打磨 skill 集）→ 抓出**日期输入框 13px 会导致 iOS Safari 整页缩放**；顺带补齐字体平滑与换行优化（`text-wrap: balance/pretty`）

**方法固定为三步**：读判据 → **写脚本实测我们自己**（不是照抄建议）→ 真缺陷修掉并加进守卫。只看不测等于没读。
纪律：**brief 优先**——碱白规范是我们的既定 brief，外部规范只提供判据，不改我们的视觉语言。

### 4. SOP 自迭代
- 每次新增红线 / 新增测试项 / 改节奏 → 回来更新本文档，版本号 +0.1
- 末尾维护变更记录，写清楚**因为什么事故或什么发现而改**
- 每月大复盘时检查：哪条 SOP 从没被执行过？要么删掉，要么找出没执行的原因
- **只增不减 = 官僚化**。每次加新规则时，看看有没有旧规则可以合并或删除；SOP 篇幅长期失控就是失效的信号

## 七·五、防止 SOP 长出死条文

这次审计发现 17 条里 5 条从未执行。规律很清楚：

> **有工具强制的全都在跑，靠「我记得做」的一条没跑。**

所以立两条规矩：

1. **新增流程必须同时给出执行方式**——是脚本、是测试项、还是并进已有动作。给不出的，说明它注定是死条文，不要写进来。
2. **定期审计执行情况**，方式是查痕迹而不是凭印象：有没有产出文件、有没有测试项、有没有日志记录。零痕迹的条目要么工具化，要么删掉。

判断标准很简单：**这条流程如果我忘了，会有东西提醒我吗？** 没有，就是死条文。

## 八、沟通约定

- **提问题给现象就够**：截图 + 一句话，根因是我的活
- **我不说"应该没问题"**：要么给验证过程，要么明说没验证
- **不做假东西**：假按钮、占位符、"即将上线"、承诺可加却加不了 — 一律不交付
- **不擅自扩大范围**：你说改 A 我不顺手改 B；B 确实该改我先说，你定
- 中文交流，移动端优先，微信是第一交付渠道
